River Crossing Puzzle

A classic puzzle — get a father, a mother, two sons, two daughters, a servant and a dog across the river in a boat that seats two. Rule checking, a proof of the shortest solution, and the animation are all plain JavaScript with no libraries.

You can actually play it

It has its own standalone page. See if you can do it in 17 crossings.

Play

What it is

A playable version of the classic river-crossing puzzle known in English as the "jealous husbands" problem. The father harms a daughter if the mother is absent, the mother harms a son if the father is absent, and the dog attacks the whole family if the servant is absent. The boat seats two and only the father, the mother and the servant can row it.

The game is HTML, CSS and JavaScript only — no framework, no animation library. It wanted a look of its own rather than the portfolio's, so it lives on a standalone page where someone arriving from a search can simply play.

One definition of "safe"

The easiest thing to get wrong here is letting the definition of a legal position exist in two places. If the game loop checks the rules one way and the solver checks them another, the two will eventually disagree.

So there is exactly one pure function: it takes the set of people on a bank and returns the list of violations. The game and the solver both call it. There is one place to change if the rules change, and the board's behaviour can never drift from what the search believes.

Proving 17 is optimal

The puzzle can be solved in 17 crossings, and the code itself establishes that this is the minimum.

Each of the eight characters is on one bank or the other — 28 = 256 arrangements — times two positions for the boat, giving 512 states in total. Each state packs into a single integer (a bitmask of who is on the far bank, shifted, plus one bit for the boat) and a breadth-first search walks the legal ones. The state space is small enough that it resolves instantly in the browser, and it shows that no solution of 16 or fewer exists.

The search is exposed as part of the board's public API, so it can re-solve for the shortest path from whatever position the player is actually in. It is not replaying a canned answer, so it stays correct no matter how far someone has wandered.

Keeping the DOM and the state in step

Boarding and disembarking use FLIP. Measure every tile before the change; in the DOM, simply appendChild the element from the bank's container into the boat's; measure again, apply the inverse transform for one frame, then animate it to zero.

The point is that there is no second source of truth for where things appear. Computing coordinates by hand and absolutely positioning the tiles would invite exactly the class of bug where the visual state and the game state disagree. Here the DOM's parent-child structure is the only answer to "where is this person", so rebuilding the board for an undo or a restart cannot desynchronise it.

What went wrong along the way

  • Undo was broken. The history snapshot was taken after Cross was pressed, so it restored the two passengers as still sitting in the boat, which left the game unplayable. Fixing it meant normalising boat occupants back onto their departure bank at snapshot time, so an undo always restores an empty boat.
  • The servant's apron never rendered. CSS selectors do not reach inside the shadow tree that <use> creates, so .rc-cut { fill: ... } simply never applied. Custom properties do inherit through it, so writing fill: var(--rc-cut) directly on the symbol's paths fixed it — and made the servant distinguishable from the father.
  • The board's proportions. At 1280px the river was 820px wide and the banks were cramped. Capping the board's width and switching the banks to three columns on wide screens fixed the balance. The opposite problem appeared on phones, where the boat only travelled 24px and never read as "crossing"; trimming the padding around the banks bought back the distance.

Details

  • Characters: SVG silhouettes. Adults and children differ in height, skirts and trousers do the rest, and the servant gets an apron and a bow tie. The three who can row are outlined in vermilion.
  • Stopwatch: timed from the difference between performance.now() readings and driven by requestAnimationFrame, but only touching the DOM when the tenths digit changes. Time away from the tab still counts, which is what you want from a wall clock.
  • Records: fewest moves and fastest time are stored separately in localStorage, so a fast run in 18 moves is still worth something.
  • Accessibility: characters are <button> elements, so the whole game is keyboard playable. Moves and incidents are announced through a live region, and the OS "reduce motion" setting is respected.
  • Verification: Playwright drives a real browser through the optimal 17-move solution, all three rule violations, undo, the two-seat limit, the no-pilot case and a 375px viewport.

Origins

A classic river-crossing puzzle, called the "jealous husbands" problem in English and 猛獣家族の川渡り in Japanese. It extends the familiar wolf, goat and cabbage riddle: eight characters instead of three, and only some of them can row, which is what makes it genuinely hard.
